### [2026-07-05 09:00] Fix-pack (post-AR) — REVOKE column-level de SELECT es un NO-OP (BLQ-ALTO-1)
- **Error**: en la migración de Fase B usé `REVOKE SELECT (col) ON creator_profiles FROM anon, authenticated` para cerrar el cross-read de las 4 columnas financieras. No cierra nada: el cross-read seguía abierto.
- **Causa raíz**: el default-ACL de Supabase otorga `SELECT` **table-level** a `anon`/`authenticated` sobre toda tabla. Un `REVOKE` **column-level** solo elimina grants column-level; el grant table-level (más amplio) sigue haciendo legibles TODAS las columnas. Column-level solo restringe cuando NO existe grant table-level.
- **Fix**: patrón correcto (mismo que `20260702020000` y el fix `anon` de hoy) = `REVOKE SELECT ON creator_profiles FROM anon, authenticated` (table-level) + `GRANT SELECT (<columnas seguras>)` column-level. Las 4 columnas financieras se OMITEN de todo GRANT → solo `service_role`. `authenticated` necesita `onboarding_*` (dashboard propio); `anon` no. Verificar la lista de "seguras" contra el DDL real = TODAS las columnas menos las 4 financieras (si falta una, se rompe catálogo/discovery).
- **Aplicar en**: cualquier cierre de cross-read/PII column-level sobre una tabla con RLS `USING(true)` (catálogo público) en Supabase. NUNCA confiar en `REVOKE (col)` de SELECT para cerrar acceso: primero `REVOKE` table-level, después `GRANT` de las columnas permitidas. Un `REVOKE column-level` de INSERT/UPDATE sí es efectivo cuando no hay path de escritura table-level relevante (los writes van por RPC/service_role), pero el de SELECT no.

# S0 — UX-09: Editor Visual de Capabilities en /publish

**Epic:** UX — Experiencia del Creator  
**Sprint:** 5  
**Prioridad:** P1 (mayor barrera actual para onboarding de creators no-técnicos)  
**Estimado:** 2–3 días  
**Estado:** PENDING_HU_APPROVED

---

## Historia de Usuario

Como creator publicando mi agente en WasiAI,  
quiero poder definir las capabilities de mi agente usando un formulario visual con campos Name, Description, InputType, OutputType, Example Input y Example Output,  
para no tener que escribir JSON crudo que no entiendo.

---

## Contexto y Motivación

Actualmente el campo de capabilities en `/publish` es un textarea de JSON crudo. La mayoría de creators (aunque sean developers) cometen errores de sintaxis JSON, no saben qué estructura usar, y abandonan el formulario. Las capabilities son la descripción que los consumidores y agentes autónomos leen para entender qué hace el agente.

---

## Criterios de Aceptación (ACs)

### AC1 — Reemplazar textarea JSON por formulario visual
- [ ] El textarea de JSON de capabilities desaparece del formulario `/publish`
- [ ] En su lugar: lista de capabilities, cada una con un card expandible
- [ ] Cada capability card tiene los campos:
  - `Name` (text, obligatorio, placeholder: "text-summarizer")
  - `Description` (textarea, obligatorio, placeholder: "Summarizes any text to N sentences")
  - `Input Type` (select: `text | json | url | image | audio | any`)
  - `Output Type` (select: `text | json | markdown | code | any`)
  - `Example Input` (textarea opcional, placeholder: "Summarize this: ...")
  - `Example Output` (textarea opcional, placeholder: "Here is a 3-sentence summary: ...")

### AC2 — Agregar y eliminar capabilities
- [ ] Botón "Add Capability +" debajo de la lista → agrega un nuevo card vacío
- [ ] Botón "Remove" (ícono trash) en cada card → elimina esa capability
- [ ] Mínimo 0 capabilities (campo opcional)
- [ ] Máximo 10 capabilities (bloquear "Add" al llegar al límite)
- [ ] Orden drag-and-drop es deseable pero NO requerido para este sprint

### AC3 — Conversión automática a JSON
- [ ] El formulario visual convierte automáticamente el estado de los cards al JSON que la API espera
- [ ] Estructura JSON resultante: `[{ "name": "...", "description": "...", "input_type": "...", "output_type": "...", "example_input": "...", "example_output": "..." }]`
- [ ] El JSON se envía al servidor exactamente igual que antes (sin cambios en la API)

### AC4 — Carga de capabilities existentes
- [ ] Si el agente ya tiene capabilities (modo edición), los cards se pre-populan correctamente
- [ ] Si `capabilities` en DB es JSON válido → parsear y renderizar cards
- [ ] Si `capabilities` es null o inválido → formulario vacío sin error

### AC5 — Fallback para creators técnicos (opcional, nice-to-have)
- [ ] Toggle "Vista avanzada (JSON)" que muestra el textarea JSON sincronizado con los cards
- [ ] Si el JSON manual es inválido → borde rojo en textarea, sin afectar el estado de los cards
- [ ] **NOTA:** Este AC es opcional. Si el esfuerzo supera 0.5 días, omitir.

### AC6 — Validación
- [ ] Si `name` está vacío en una capability → error inline al hacer submit
- [ ] Si `description` está vacío en una capability → error inline al hacer submit
- [ ] Cards con errores muestran borde rojo y mensaje debajo del campo

---

## Scope (qué SÍ incluye)

- Componente `CapabilitiesEditor` (nuevo) en `/publish`
- Integración en el formulario multi-paso existente (Step correspondiente)
- Conversión bidireccional estado ↔ JSON
- Validación client-side de campos obligatorios

## Out of Scope

- Drag-and-drop para reordenar (Sprint 6)
- Cambios en la API (mismo JSON enviado al servidor)
- Capabilities pre-definidas por categoría (roadmap)
- Preview en tiempo real de cómo se ven las capabilities en la ficha del agente

---

## Riesgos

| Riesgo | Probabilidad | Impacto | Mitigación |
|--------|-------------|---------|------------|
| Estructura JSON actual en DB inconsistente → carga falla | Media | Medio | Parsear con try/catch, fallback a array vacío |
| Esfuerzo del AC5 (toggle JSON) consume tiempo extra | Alta | Bajo | Omitir AC5 si supera 0.5 días adicionales |
| Componente grande se vuelve difícil de mantener | Baja | Bajo | Separar en `CapabilityCard.tsx` + `CapabilitiesEditor.tsx` |

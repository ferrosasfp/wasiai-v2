## Context

El creator hace withdraw desde `/creator/dashboard`. Si tiene agentes en DB pero no on-chain, `claimEarnings` falla silenciosamente porque el contrato no reconoce esos agentes.

**Flujo real:** Registrar on-chain es PRE-REQUISITO para que futuros settlements acumulen `earnings[creator]`. El withdraw solo es posible DESPUÉS de que el operador ejecute un settlement post-registro. Por tanto el flujo es:
1. Registrar agentes off-chain via `batchSelfRegister`
2. Esperar a que haya earnings acumulados (settlement post-registro)
3. Withdraw earnings

**Implicación UX:** El Paso 1 (registro) y el Paso 2 (withdraw) NO ocurren en la misma sesión. Después de registrar, el usuario ve "Earnings: $0.00" hasta que el operador corra settlement. El withdraw se habilita cuando `pendingEarnings > 0`.

## Wave 1 — Backend: on-chain-status endpoint

### W1.1 Crear `src/app/api/creator/agents/on-chain-status/route.ts`
```
GET /api/creator/agents/on-chain-status
Auth: Supabase session (authenticated creator)
Response: { registered: string[], unregistered: string[] }
```

Lógica:
1. Obtener user via Supabase auth
2. Query `agents` table: `SELECT slug FROM agents WHERE creator_id = user.id AND status = 'active'`
3. Para cada slug, llamar `isAgentRegisteredOnChain(slug)`
4. Separar en registered/unregistered
5. Retornar JSON

## Wave 2 — Frontend: WithdrawButton 2 pasos

### W2.1 Refactor `WithdrawButton.tsx`

Nuevo state machine:
```
idle → checking → (needsRegistration | readyToWithdraw | noEarnings)
  needsRegistration → registering → confirming_reg → registered (show success msg)
  readyToWithdraw → requesting_voucher → signing → confirming_tx → success
  noEarnings → disabled (tooltip)
```

Pasos:
1. Al montar, fetch `/api/creator/agents/on-chain-status`
2. Si `unregistered.length === 0 AND pending > 0` → withdraw habilitado (flujo actual)
3. Si `unregistered.length > 0` → mostrar banner de registro (independiente de pending)
4. Si `unregistered.length === 0 AND pending === 0` → botón deshabilitado con tooltip "Acumula earnings primero"

**CLAVE:** Registro y withdraw son acciones SEPARADAS en la UI, no pasos secuenciales de un mismo flujo. El registro puede ocurrir días antes del primer withdraw.

### W2.2 Step 1 — Registro on-chain
- Leer `registrationFee` del contrato (si existe, o hardcode 0 para V2 inicial)
- Estimar gas via `estimateContractGas`
- Mostrar: "Registrar N agentes — Gas estimado: X AVAX"

- **Limit 50 slugs/tx** (contrato limita a 50). Si `unregistered.length > 50`, paginar en chunks de 50 y ejecutar txs secuenciales.
- Al confirmar: `writeContract({ functionName: 'batchSelfRegister', args: [slugs, prices, erc8004Ids] })`
- Polling con `waitForTransactionReceipt` timeout 30s
- Si timeout: mostrar "Tx pendiente" + link a Snowtrace
- Si revert: mostrar error con slug problemático
